01

Key findings

These are the four findings that matter for a toolkit decision. Everything after this section is supporting documentation: approaches, comparison, verification, criteria, a sample record, and the full dataset.

Finding 1

Access is the gate, not API existence

—/100 apps report a public API. —/100 have a self-serve free or trial credential route. The remaining apps face commercial or administrative restrictions.

Paid / review / admin / sales gated—
No public API—
Access model unresolved—
Free or trial route—

Free trials do not necessarily mean API credentials are included.

Main takeaway: the challenge is not whether an API exists. It is whether a developer can actually obtain credentials and use it. Toolkit building needs an access and commercial workstream in addition to engineering.
Finding 2

Ecommerce is a toolkit coverage gap

Only —/10 Ecommerce apps match an existing Composio toolkit. This is the largest category-level coverage gap.

Productivity coverage—/10
CRM coverage—/10
Developer infrastructure—/10
Ecommerce coverage—/10
Main takeaway: Ecommerce is the clearest opportunity for expanding toolkit coverage.
Finding 3

Category maturity is uneven

The same 100 apps do not represent one uniform integration problem. Readiness groups are visible in the Research Agent results:

Most ready

CRM: —/10 easy. Communications: —/10. Developer infrastructure: —/10. Productivity: —/10.

Mixed maturity

Support, Marketing and Ecommerce each split five easy / five moderate in the Research Agent results.

More heterogeneous

Finance: — easy, — moderate, — hard. AI/media: — easy, — moderate, — hard, — blocked.

Main takeaway: toolkit development should not be approached uniformly across all categories. Some categories have fewer access restrictions and more consistent APIs; others have more gating and uncertainty.

02

Research approaches

Two separate approaches were used. They are named consistently throughout this document.

Composio MCP+OpenCode

Initial approach
  1. Connected Composio MCP.
  2. Used the web search tool for research.
  3. Connected the workflow to a Google Sheet containing 100 applications.
  4. Wrote a research strategy prompt.
  5. Used the prompt and tools to research the applications and populate the results.
This produced the Google Sheet research tab that is compared against the Research Agent output.

Research Agent

Second approach
  1. Built using the Composio SDK.
  2. Used Exa search for research.
  3. Created a verification pipeline.
  4. Ran the research again.
  5. Compared the results against the initial Composio MCP+OpenCode findings.
The verification pipeline was slow, and I was running out of time. As a result, I ran it through one pass and compared the results.

05

Comparison observations

These are notes from comparing the two approaches. They are not additional key findings.

  • The differences between the two research processes are not very large overall.
  • Most inconsistencies seem to come from what each approach considers “buildable”.
  • The Research Agent needs more work. The factors and criteria it considers should be modified to improve the results.
  • Composio MCP+OpenCode appears to consider some additional relevant features and may capture more useful application-specific information in certain cases.
  • There are a few outliers, particularly Sherlock and Paygent Connect, where the available information was insufficient or the context was missed.
  • For Sherlock, the important detail is that it is a CLI project and could potentially be wrapped as an agent-callable skill.
  • For Paygent Connect, the underlying NMI-powered relationship should have been investigated instead of focusing only on Paygent-specific information.
